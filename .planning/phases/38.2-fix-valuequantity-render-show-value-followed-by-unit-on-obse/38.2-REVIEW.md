# Phase 38.2: Code Review Report

**Reviewed:** 2026-04-29
**Depth:** standard
**Files Reviewed:** 2
**Status:** issues_found (3 Info, 0 Warning, 0 Critical)

## Summary

The Phase 38.2 fix correctly addresses the rendering gap surfaced during the Phase 38.1 re-walk: UCUM-coded `valueQuantity` instances now render `<value> <unit>` (e.g. `98 mg/dL`) instead of being captured by the standalone-Coding branch and showing only the unit code. The new dispatch ordering, the shape-detection predicate, and the four regression tests are sound.

Branch-ordering correctness was the key risk and has been handled deliberately:

- **CodeableConcept** (line 103, `obj.coding || obj.text`) fires before Quantity — correct: a Quantity has neither `coding` nor `text`.
- **Quantity** (lines 127-142, new) fires before standalone Coding — correct: UCUM Quantities carry `{ system, code }` and would otherwise be swallowed.
- **Standalone Coding** (line 145, `obj.system && obj.code`) is now reached only when no `unit` is present and `value` is non-numeric.
- **Identifier** (line 171, `obj.value && (obj.system !== undefined || obj.type !== undefined)`) is unaffected because `Identifier.value` is a string, and the Quantity predicate's `value`-arm requires `typeof obj.value === 'number'`.

The four-shape test matrix (full / value-only / unit-only / empty) covers the renderable axes correctly. Anti-regression assertions in tests 3 and 4 (no bare `mg/dL` in the row, no phantom unit string) are scoped to the `valueQuantity` row via `closest('tr')`, which is the right approach. No security, correctness, or maintainability defects were found. The findings below are minor refinements, not blockers.

## Info

### IN-01: Quantity with `code` but no `unit` falls through to value-only rendering

**File:** `src/components/explorer/ResourcePropertyTable.tsx:127-142`
**Issue:** FHIR R4 Quantity allows `{ value, system, code }` without a human-readable `unit`. UCUM-conformant resources sometimes omit `unit` and rely on the `code` (which for UCUM IS human-readable, e.g. `mg/dL`). Under the current predicate, such a payload is shape-matched (numeric `value`, no `coding`) but `hasUnit` is false, so only the value is rendered. The information loss is mild (no measurement is misrepresented), but the displayed result is less informative than it could be.
**Fix:** Optionally fall back to `obj.code` when `unit` is absent:
```tsx
const hasUnit = typeof obj.unit === 'string' && obj.unit.length > 0;
const fallbackUnit =
  !hasUnit && typeof obj.code === 'string' && obj.code.length > 0
    ? (obj.code as string)
    : undefined;
if (hasValue && (hasUnit || fallbackUnit)) {
  return <Text size="sm">{obj.value as number} {(obj.unit as string) ?? fallbackUnit}</Text>;
}
```
This is an enhancement, not a defect — the current code is correct for the spec'd contract. Defer to the team's preference.

### IN-02: `as number` cast in value-only branch is not gated on `typeof value === 'number'`

**File:** `src/components/explorer/ResourcePropertyTable.tsx:137`
**Issue:** The `isQuantityShape` predicate has two arms; the first arm (`typeof obj.unit === 'string'`) admits objects whose `value` is non-numeric (e.g. `{ unit: 'mg/dL', value: 'abc' }` — non-conformant but technically possible from arbitrary upstream data). When `hasValue` is true but `hasUnit` is false, line 137 emits `{obj.value as number}`. React coerces with `String()` so the visual output is fine, but the cast is misleading and could trip a future maintainer relying on the type assertion.
**Fix:** Tighten `hasValue` to assert numeric type, mirroring the predicate:
```tsx
const hasValue = typeof obj.value === 'number';
```
This also makes the `0` case (already handled via `!== null/undefined`) explicit, since `typeof 0 === 'number'`.

### IN-03: `!obj.coding` would mismatch a defensively-empty `coding: []` array

**File:** `src/components/explorer/ResourcePropertyTable.tsx:129`
**Issue:** The second arm of the predicate (`typeof obj.value === 'number' && !obj.coding`) uses truthy/falsy negation. An empty array `[]` is truthy in JavaScript, so `!obj.coding` is `false` when `obj.coding === []`. A pathological payload like `{ value: 42, coding: [] }` (non-FHIR-conformant — validators normally drop empty cardinality-0 arrays) would NOT be detected as Quantity shape and would fall through to subsequent branches. The CodeableConcept branch above (line 103, `obj.coding || obj.text`) would also reject it (`[]` is truthy but the branch renders nothing useful when `codings` is empty and there's no `text`). Net effect: the value `42` is silently dropped. Highly unlikely in practice but worth a tightening:
```tsx
const hasCodingArray = Array.isArray(obj.coding) && obj.coding.length > 0;
const isQuantityShape =
  (typeof obj.unit === 'string') ||
  (typeof obj.value === 'number' && !hasCodingArray);
```
Defer if upstream data shape is trusted.
