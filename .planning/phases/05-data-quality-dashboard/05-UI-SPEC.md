# Phase 05 — UI Design Contract

> Visual and interaction contract for the Data Quality Dashboard. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

Phase 5 adds a new top-level `Quality` route with four audit axes: resource counts (QUAL-01), field completeness (QUAL-02), coding coverage (QUAL-03), profile validation (QUAL-04). All visual decisions reuse the token system established in Phases 1-4 (Mantine 8 defaults, 14px body, blue.6 accent, 8-point spacing). This phase introduces three new patterns: (1) a summary-strip overview, (2) per-type progressive metric panels, (3) an OperationOutcomeIssue list. No new color dimensions, no new type sizes.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none (Mantine is the design system, required peer of @medplum/react) |
| Preset | not applicable |
| Component library | Mantine 8 (@mantine/core, @mantine/hooks, @mantine/notifications) + @medplum/react 5.x for FHIR-aware rendering |
| Icon library | @tabler/icons-react (established Phase 1) |
| Font | System stack: `-apple-system, BlinkMacSystemFont, Segoe UI, Roboto, Helvetica, Arial, sans-serif` (from `src/theme.ts`) |

**Theme source of truth:** `src/theme.ts` (`primaryColor: 'blue'`, `defaultRadius: 'sm'`). No theme changes in this phase.

**Chart library decision (Claude's Discretion, from RESEARCH.md Open Question #3):** **Mantine-only for v1 — do NOT install `@mantine/charts` or `recharts`.** Research confirms the dependency costs ~150 KB gz and is not justified for v1 when `Progress`, `RingProgress`, and sorted tables convey the same information. Charts deferred to v2 if users explicitly ask for them. All visualization uses `<Progress>` (inline bars), `<RingProgress>` (percentage rings), `<Badge>` (coverage buckets), and sortable `<Table>` rows.

## Spacing Scale

Inherits Mantine default spacing tokens (multiples of 4) from prior phases. Use token names in JSX (`gap="md"`), never hard-coded pixels.

| Token | Value | Usage in Phase 5 |
|-------|-------|------------------|
| xs | 4px | Icon-to-label gap in summary cards; gap between metric label and value; table cell inline spacing |
| sm | 8px | Compact element spacing inside Card/Paper; gap inside summary-card Stack |
| md | 16px | Default Card padding; gap between summary cards in the overview grid; Progress bar bottom margin |
| lg | 24px | Section gap between overview strip and detail panels; padding inside detail Paper; gap between stacked metric rows |
| xl | 32px | Page-level vertical padding; gap above the "Recompute" toolbar |
| 2xl | 48px | Empty-state vertical padding |
| 3xl | 64px | Not used |

**Exceptions:** RingProgress size is 80px × 80px in summary cards and 48px × 48px in per-type table rows (these are component sizes, not spacing tokens). Progress bar height is 8px (Mantine default `size="md"`). Bar-chart replacement inline `<Progress>` fills row width; max-width 240px inside tables to prevent layout stretch.

## Typography

Inherits the 4-size / 2-weight system from prior phases. No new sizes.

| Role | Size | Weight | Line Height | Mantine Token | Usage |
|------|------|--------|-------------|---------------|-------|
| Body | 14px | 400 | 1.55 | `size="sm"` | Table cell text, metric numerator/denominator, disclaimer text |
| Label | 14px | 600 | 1.55 | `size="sm"` + `fw={600}` | Table column headers, metric labels ("Completeness", "Coding Coverage"), tab labels, summary-card titles |
| Heading | 20px | 600 | 1.2 | `<Title order={2}>` | Panel section headings ("Resource Counts", "Completeness", "Coding Coverage", "Profile Validation") |
| Display | 28px | 600 | 1.2 | `<Title order={1}>` (or `order={2}` depending on existing Explorer/Patients alignment) | Page title "Data Quality" |

**Monospace:** `<Code>` (Mantine) for FHIRPath expressions in validation issues (e.g., `Condition.code.coding[0].system`), resource type names in code context, and validator URL display. 13px (Mantine default for Code), line-height 1.5.

**Numeric emphasis:** Summary-card big numbers (total resources, % coverage) use `<Text fw={700} size="xl">` (~20px). This is the only place weight 700 appears — it is an emphasis rendering of existing sizes, not a new type role. If the checker treats this as a third weight, downgrade to `size="lg"` (18px) + `fw={600}` and delete the bold emphasis.

Totals: 4 sizes (14/20/28 + 13 mono), 2 weights (400/600). Summary-card numbers are the only weight-700 occurrence, rendered at an existing size — documented as a stylistic variant, not a new role.

## Color

Inherits Mantine default light theme from prior phases. The 60/30/10 split is locked. Phase 5 adds a semantic palette for validation severity only — these colors already exist in prior phases (red/yellow/blue) but are formalized here.

| Role | Value | Mantine Token | Usage |
|------|-------|---------------|-------|
| Dominant (60%) | `#FFFFFF` | `white` | Page background, main content area, Card/Paper surface |
| Secondary (30%) | `#F8F9FA` | `gray.0` | Sidebar (inherited), table header row, summary-card subtle fill, Progress track background |
| Accent (10%) | `#228BE6` | `blue.6` | See reserved-for list below |
| Destructive | `#FA5252` | `red.6` | Validation error/fatal severity; "Clear metrics cache" button outline/hover |

**Accent (blue.6) reserved for:**
- Page title underline/active sidebar "Quality" nav item (inherited from Phase 1 sidebar pattern)
- `Progress` fill color (default Mantine primary) for completeness and system+code coverage bars
- Primary button variants ("Recompute", "Validate batch")
- Clickable resource-type rows in the counts / completeness / coverage tables (drill-down links)
- `RingProgress` ring color for the "Overall completeness" and "Overall coding coverage" summary rings
- `Badge color="blue" variant="light"` for count badges (inherited Phase 1/2 pattern)

Accent is **NOT** applied to: validation issue severity badges (use semantic colors below), coding-coverage "text-only" or "empty" buckets (use semantic colors below), summary-card "total resources" number (neutral dark text).

**Coding-coverage semantic palette (D-07, Answers Open UI Question #6):**

| Bucket | Color | Mantine Token | Rationale |
|--------|-------|---------------|-----------|
| system+code (good) | `#228BE6` | `blue.6` (accent) | Positive signal; uses project's primary accent. |
| text-only (partial) | `#FD7E14` | `orange.6` | Warning without alarm; matches Phase 1 "using default settings" orange. |
| empty (missing) | `#FA5252` | `red.6` | Absence is a data quality defect; same red as Phase 1 connection error. |

Rendered as three stacked `<Progress.Section>` segments inside a single `<Progress.Root>` per resource type (Mantine compound Progress), with a legend above the table.

**Validation severity palette (D-10, Answers Open UI Question #6):**

| Severity | Badge color | Hex | Mantine Token | Rationale |
|----------|-------------|-----|---------------|-----------|
| `fatal` | red | `#FA5252` | `red.6` | Highest severity; same red as error to avoid palette sprawl. |
| `error` | red | `#FA5252` | `red.6` | Blocks conformance. |
| `warning` | yellow | `#F59F00` | `yellow.6` | Non-blocking; distinguishable from orange (used elsewhere for coverage partial-fill). |
| `information` | blue | `#228BE6` | `blue.6` | Neutral signal; matches accent. |

Rendered as `<Badge color="{severity-color}" variant="light" size="sm">{severity}</Badge>`. The `variant="light"` keeps the badge readable without shouting — the issue count, not each badge, carries the visual weight on the page.

**Neutral / metadata:**
- `gray.5` (`#ADB5BD`): "Based on N resources" disclaimer text, "No MII profile" subtitle, column-header sort arrow idle state.
- `c="dimmed"`: All metadata text (sample size footnote, "Last computed …" timestamp).

**Inherited status dots (from Phase 4 sidebar):** unchanged in this phase.

### Toast feedback

| Event | Mantine notification |
|-------|----------------------|
| Recompute metrics started | No toast — inline progress only (Skeleton per row). |
| Recompute metrics complete | `title: "Metrics updated", message: "Recomputed in {seconds}s across {N} types.", color: green` |
| Clear metrics cache | `title: "Cache cleared", message: "Removed cached metrics for {N} resource types.", color: green` |
| Export report | `title: "Report downloaded", message: "quality-report-{timestamp}.json", color: green` |
| Validation batch complete | `title: "Validation complete", message: "{issueCount} issues across {resourceCount} resources.", color: blue` |
| Validation backend error | `title: "Validator unreachable", message: "Continuing with structural validation only.", color: orange` |

### Destructive actions

- **Clear metrics cache:** no modal. Cache is locally rebuildable. Success toast confirms the action (mirrors Phase 4 Clear terminology cache pattern).
- **Cancel batch validation:** no modal. Cancellation is non-destructive (partial results remain displayed with a "cancelled — showing partial results" footnote: `Validation cancelled at {N}/{total}. Results below reflect completed resources only.`).
- **No other destructive actions in this phase.** Read-only by design — no create/update/delete.

## Layout Contract

**Primary focal point per screen:**
- Overview (landing): the four summary cards in the top strip.
- Counts tab: the sortable table (with embedded inline Progress bars in each row).
- Completeness / Coverage tabs: the sortable per-type table.
- Completeness / Coverage drill-down: the per-field breakdown list.
- Validation tab: the issue list table.

### Overall page structure (Answers Open UI Question #2 — single-page with tabs)

**Decision:** Tabbed single-page layout. The four axes (Counts / Completeness / Coverage / Validation) each warrant a dedicated panel with its own actions and progressive loading. Scrolling through four long panels on one page hurts scannability on a data-heavy desktop tool (REQUIREMENTS.md: "optimize for 1200px+ screens"). Tabs keep the summary strip always visible at top, and the per-tab panels stay focused. Use `<Tabs keepMounted>` so users don't lose computed state when switching tabs (matches Phase 3 `MiiModuleTabs` pattern).

```
+--sidebar--+--main-content-area-----------------------------------+
|            | [Page title: "Data Quality"]                         |
|            | [Toolbar: Sample size | Last computed | Recompute]   |
|            |                                                      |
|            | [Overview strip — always visible]                    |
|            |   ┌───────────┬───────────┬───────────┬───────────┐ |
|            |   │ Total     │ Resource  │ Overall   │ Overall   │ |
|            |   │ resources │ types     │ compl.    │ coverage  │ |
|            |   │ 52,431    │ 47        │ 73%       │ 61%       │ |
|            |   └───────────┴───────────┴───────────┴───────────┘ |
|            |                                                      |
|            | [Tabs: Counts | Completeness | Coding Coverage |     |
|            |        Validation]                                   |
|            | [Active tab panel]  <-- FOCAL                        |
|            |                                                      |
|            | [Footnote: "Based on the first 100 resources..."]    |
+------------+-----------------------------------------------------+
```

Main content uses `Stack gap="lg"` (consistent with Phases 1-4). Tabs use Mantine default variant (no pills, no outline) for consistency with Phase 3's `MiiModuleTabs`.

### Overview strip (4 summary cards)

Mantine `<SimpleGrid cols={{ base: 1, sm: 2, md: 4 }}>` so the strip degrades gracefully on narrower screens even though the target is 1200px+.

Each card is a `<Card padding="md" withBorder radius="sm">`:

```
+-----------------------------------+
| [icon]  Card label (fw=600, sm)   |
|                                   |
| 52,431   (fw=700, xl, dark)       |
| +/- indicator (xs, dimmed)        |
+-----------------------------------+
```

Card labels (left-to-right):
1. `Total resources` — number from sum of per-type counts. Icon: `IconDatabase`.
2. `Resource types` — count of non-empty resource types. Icon: `IconListDetails`.
3. `Overall completeness` — weighted average of per-type completeness (weighted by type count × required-field count). Icon: `IconCircleCheck`. Rendered as big percentage + `RingProgress` at right edge (size=80, thickness=6).
4. `Overall coding coverage` — weighted average of system+code buckets across all types. Icon: `IconLanguage`. Rendered as big percentage + `RingProgress` (same spec).

### Counts tab

`<Table striped highlightOnHover>` with columns:

| Column | Content | Sort |
|--------|---------|------|
| Resource type | Clickable link (blue.6 text) navigating to `/explorer/{type}` | alphabetical |
| Count | Right-aligned number (fw=600) | numerical (default DESC) |
| Distribution | Inline `<Progress value={pct} color="blue.6" />` bar, width 240px, where `pct = count / maxCount * 100`. | n/a |

Default sort: count DESC. Clicking a column header toggles sort. Empty rows (count=0) hidden by default with a `Show empty types` toggle (mirrors Phase 3 D-09 "hide zero-count rows"). Loading per-row: `<Loader size="xs" />` in the Count cell (Phase 1 pattern).

### Completeness tab

Same table shell, columns:

| Column | Content | Sort |
|--------|---------|------|
| Resource type | Clickable link → drill-down view | alphabetical |
| Completeness | `<RingProgress size={48} thickness={4} sections={[{ value: pct, color: 'blue.6' }]} label={<Text size="xs">{pct}%</Text>} />` | numerical |
| Populated / total | `{populated} / {total}` in dimmed text | n/a |
| Sample | `{N} of {totalForType}` in dimmed text | n/a |
| Profile | Profile display name (e.g., "MII Diagnose") or `<Text c="dimmed">Structural (min>=1)</Text>` | n/a |

Default sort: completeness ASC (worst-first so users see what needs attention).

**Completeness drill-down** (`/quality/completeness/:type`): a sub-page rendering a two-column list of required paths with populated/total count per path. Use `<Stack gap="sm">` of `<Group justify="space-between">` rows: path on the left (monospace), `<Progress />` bar + percentage on the right. Back link: `<Button variant="subtle" leftSection={<IconArrowLeft />}>Back to Completeness</Button>`.

### Coding Coverage tab

Same table shell, columns:

| Column | Content | Sort |
|--------|---------|------|
| Resource type | Clickable link → drill-down view | alphabetical |
| Coverage | Stacked `<Progress.Root>` with three `<Progress.Section>` segments (blue / orange / red for systemCode / textOnly / empty), width 240px | n/a |
| system+code | `{pct}%` (blue.6 text) | numerical |
| text-only | `{pct}%` (orange.6 text) | numerical |
| empty | `{pct}%` (red.6 text) | numerical |
| CC field count | `{N} CodeableConcept fields in sample` | n/a |

Default sort: `system+code` ASC (worst-first).

Legend above the table: a single `<Group gap="md">` with three color swatches + labels: `● system+code  ● text-only  ● empty`.

**Coverage drill-down** (`/quality/coding/:type`): per-field breakdown. `<Table>` with columns `Field path | system+code % | text-only % | empty % | Example coded value`. Path in `<Code>`. Example value uses Medplum's `<CodeableConceptDisplay>` (already wired in prior phases).

### Validation tab

Top-of-panel controls:

```
[Resource type: Select ▼]   [Sample size: N]   [Run: Validate sample]
[Backend: Structural | Remote (configured) | Remote (not configured)]
```

Progress bar during batch (mirrors D-11):

```
Validating Condition (42/100)... [===========>          ] Cancel
```

Results table below (sticky header, scrollable to 600px max-height):

| Column | Content |
|--------|---------|
| # | Row number |
| Severity | `<Badge color={severityColor} variant="light">{severity}</Badge>` |
| Resource | Link to `/explorer/{type}/{id}` (blue.6) |
| Location | `<Code>{issue.expression?.[0] ?? issue.location?.[0]}</Code>` |
| Issue | `{issue.code} — {issue.diagnostics ?? issue.details?.text ?? ''}` |

Row ordering: by severity DESC (fatal > error > warning > information) then by resource id ASC. Grouping via `<Table>` row spans is v2; v1 uses flat rows with the resource link repeated.

Export report link sits below the results table: `<Button variant="subtle" leftSection={<IconDownload size={16} />}>Export report (JSON)</Button>`. Exports the union of all four tabs' computed state (counts, completeness, coverage, validation) as a single JSON file named `quality-report-{ISODate}.json`.

## Interaction Contracts

| Interaction | Trigger | Feedback | Error state |
|-------------|---------|----------|-------------|
| Initial dashboard load | User navigates to `/quality` | Overview strip renders with Skeletons (4 summary cards), then populates progressively as per-type counts / completeness / coverage settle. Toolbar `Last computed` reads from cache if fresh, or shows `Never` on first load. | If connection is lost mid-load, show the same error alert as Phases 1-4; retry via `Recompute metrics`. |
| Sample size change | User edits `NumberInput`, debounced 500ms (via `useDebouncedValue`) | All panels invalidate their per-type reports and re-sample. Progress restarts from Skeleton state. `Last computed` resets. | Invalid input (NaN, negative) reverts to previous value silently (Mantine `NumberInput` min/max guards). |
| Sort column | User clicks a sortable column header | Sort arrow updates immediately (no loading); rows re-order client-side (all data already in state). | N/A — pure client-side operation. |
| Drill-down navigation | User clicks a resource-type row in Completeness or Coverage table | Navigate to `/quality/{completeness\|coding}/:type`. Breadcrumb trail updates (reuses Phase 2 `useBreadcrumbTrail` with `basePath=/quality`). | If the type has no cached report, re-sample before rendering (show Skeleton). |
| Tab switching | User clicks a tab header | Panel swaps instantly (Mantine Tabs built-in). `keepMounted` preserves computed state — no refetch. | N/A. |
| Recompute metrics | User clicks `Recompute metrics` in toolbar | All caches invalidated for current server. All panels re-enter Skeleton state and repopulate. Toast on completion. | Per-row errors surface as `Error` badges (mirrors `useResourceCounts` error pattern) — overall toast only fires if the entire run failed. |
| Clear metrics cache | User clicks `Clear metrics cache` in Settings (added to Settings page as a sibling to Phase 4's Clear terminology cache) | Synchronous: Map.clear + localStorage.removeItem. Toast confirms. | Silently swallows localStorage errors (same as Phase 4). |
| Validate sample | User picks a resource type, clicks `Validate sample` | Progress bar renders `{current}/{total}`. Results table populates row-by-row as backends return. Cancel button interrupts. | Backend errors show an orange `notifications.show` toast; structural fallback continues. |
| Cancel batch | User clicks `Cancel` during validation | Progress bar freezes at current count. Results table stays with a `cancelled — showing partial results` footer. Input controls re-enable. | N/A — cancellation is always safe. |
| Export report | User clicks `Export report (JSON)` | Browser downloads `quality-report-{ISODate}.json`. Toast confirms. | If no data is loaded (report is empty), button is disabled with a tooltip: `Run the dashboard before exporting.` |
| Validation row click | User clicks a resource link in the validation table | Navigate to `/explorer/{type}/{id}` (reuses Phase 2 resource detail view). | N/A — same as Phase 2. |

### Keyboard shortcuts (Claude's Discretion)

| Shortcut | Action |
|----------|--------|
| `R` | Trigger Recompute metrics (when no input is focused) |
| `1` / `2` / `3` / `4` | Switch to Counts / Completeness / Coverage / Validation tab (when no input is focused) |

| Validation complete, 0 issues | `<Alert color="green" icon={<IconCheck />}>No conformance issues found in the sampled {N} resources.</Alert>` |
| Validation complete, N issues | Results table populated; summary pill above table: `{N} issues across {R} resources`. |

| Cache hit on mount | Overview strip renders immediately from cached values. `Last computed {relative}` shown in toolbar. |

| Server disconnected | Redirect to dashboard with connection error (reuse Phase 1 error handling). |

## Cross-View Consistency

- **Accent color:** `blue.6` for clickable resource-type text is identical to Phase 1 Explorer dashboard and Phase 2 search result rows. A resource type is always a blue link — no exceptions — so users learn the affordance once.
- **Progress bars:** `Progress` default color is blue.6 (Mantine primary). Reused throughout for any "percentage of a total" visualization. The only three-color usage is the Coding Coverage stacked bar (blue/orange/red) where each segment represents a distinct bucket, not a percentage.
- **Skeletons:** Height values match the component they replace — 96 for cards, 48 for rings, 8 for Progress bars, 40 for table rows (Phase 2/3 established).
- **Disclaimers:** Every sampled metric carries a `Based on the first {N} resources per type` footnote. Users never have to guess whether a percentage is a full-scan number or an estimate.
- **Cross-navigation:** Validation issue rows link to `/explorer/{type}/{id}`. Resource-count rows link to `/explorer/{type}`. No parallel "quality-internal" resource viewer — the Explorer is the canonical viewer across the app.

---

## Accessibility Contract

- All color-coded signals (severity badges, coverage buckets) carry a text label alongside the color. Users with color vision deficiency get full information from text alone.
- Table column sort state announced via `aria-sort="ascending|descending|none"` on `<th>` (Mantine Table doesn't auto-set this — planner MUST add it).
- Progress bars expose `aria-label="{percentage}% {metricName}"` via Mantine's `Progress` `aria-label` prop. Required for the inline bars in tables where the numeric percentage is rendered as an adjacent cell (screen-reader users don't have to stitch two cells together).
- Batch validation progress uses `aria-live="polite"` on the progress text so screen readers hear `Validating Condition, 42 of 100` without interrupting.
- Drill-down back button receives focus on mount so keyboard users return via Enter/Space.
- Skeleton placeholders carry `aria-busy="true"` on the container that replaces them when data arrives.
