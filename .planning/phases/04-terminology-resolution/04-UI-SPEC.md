# Phase 4 — UI Design Contract

> Visual and interaction contract for Phase 4 (Terminology Resolution). Generated by gsd-ui-researcher, verified by gsd-ui-checker.

Phase 4 is a terminology resolver/cache phase. The UI surface is narrow: extend the Phase 1 sidebar status indicator, add a "Clear terminology cache" action and termserver URL display to Settings, and make progressive-enhancement CodeableConcept resolution visually invariant (no spinners, no layout shift). All visual decisions reuse patterns locked in Phase 1 and Phase 2.

## Spacing Scale

Mantine's default spacing tokens map to the 8-point scale. Use the token names (`xs`, `sm`, `md`, `lg`, `xl`) in JSX props, never hard-coded pixels.

| Token | Value | Usage in Phase 4 |
|-------|-------|------------------|
| xs | 4px | Gap between status dot and label (sidebar), gap between code chip and inline text |
| sm | 8px | Vertical gap between the two server-status rows in the sidebar; gap inside Settings rows |
| md | 16px | Default element spacing inside SettingsPage Paper (existing pattern) |
| lg | 24px | Section padding, gap between Settings page sections |
| xl | 32px | Spacing between the "Terminology" section and the Connection section in Settings |

**Exceptions:** none. Sidebar status dot is 8px × 8px (matches Phase 1 existing indicator — locked pattern, do not change).

## Color

Mantine's default light theme provides the 60/30/10 baseline. Phase 4 does not introduce new colors — all dots, accents, and destructive hues come from Mantine's palette tokens so future dark-theme work remains trivial.

| Role | Value | Mantine Token | Usage |
|------|-------|---------------|-------|
| Dominant (60%) | `#FFFFFF` | `white` / `gray.0` (#f8f9fa) | AppShell main background, SettingsPage background |
| Secondary (30%) | `#F8F9FA` | `gray.0` / `gray.1` | Paper surfaces (Settings cards), Code component subtle fill |
| Accent (10%) | `#228BE6` | `blue.6` (theme `primaryColor`) | See reserved-for list below |
| Destructive | `#FA5252` | `red.6` | FHIR server unreachable dot; "Clear terminology cache" button outline/hover |
| Success (health) | `#40C057` | `green.6` | FHIR / terminology server reachable dot (matches Phase 1 locked value `#40c057`) |
| Neutral (idle/not-configured) | `#ADB5BD` | `gray.5` | "Not connected" / "Not configured" status dot (matches Phase 1 locked value `#adb5bd`) |

**Accent (blue.6) reserved for:**
- Primary nav active state (existing Phase 1 behavior — do not extend)
- Primary `Button` variant (no primary blue button is introduced in Phase 4)

Accent is NOT applied to: terminology status dot, "Clear terminology cache" button, resolved/unresolved CodeableConcept values, section headings, icons in Settings.

**Destructive (red.6) reserved for:**
- FHIR server + Terminology server "unreachable" status dot
- "Clear terminology cache" button (`variant="light"` `color="red"`) — it destroys locally cached data (not server data), which is clearly recoverable, so no modal confirm; a success toast is used to confirm completion.

**Unresolved-code treatment (D-07):** wrap the raw code inside a Mantine `<Code>` (renders with light gray background and monospace font). No dashed underline, no tooltip in v1 (keeps the progressive-enhancement swap visually silent per D-12). The monospace-in-gray-pill signal is the "unresolved" affordance; a future phase may add a Tooltip when UX research validates it is needed.

## Component Contracts (Phase 4 additions)

Because Phase 4 extends existing components rather than introducing new full pages, the contract below is prescriptive at the per-surface level.

### C-1: Sidebar status block (extends Phase 1 `Sidebar.tsx`)

Replace the single-row status indicator with a two-row vertical stack, both rows using the exact same 8px dot pattern as Phase 1.

Layout (inside the existing top `AppShell.Section`):

```
FHIR Exploder                       ← Text fw={600} size="lg"  (unchanged)
● FHIR server: Connected            ← Group gap="xs"   (8px dot + Text size="xs" c="dimmed")
● Terminology: Reachable            ← Group gap="xs"   (8px dot + Text size="xs" c="dimmed")
```

- Outer wrapper: `<Stack gap="xs" mt="xs">` containing two `<Group gap="xs">` rows.
- Dot component: `<Box>` with `width: 8, height: 8, borderRadius: '50%', backgroundColor: <status.color>`. Reuse `STATUS_CONFIG` map; add a matching `TERMINOLOGY_STATUS_CONFIG` that maps `reachable → #40c057`, `unreachable → #fa5252`, `probing → #adb5bd` (with `pulse: true`), `not-configured → #adb5bd` (`pulse: false`).
- No tooltip. Labels are always visible — accessibility covered.
- Animation: `pulse` keyframe already exists in project CSS; reuse unchanged.

### C-2: Settings — Terminology section (extends Phase 1 `SettingsPage.tsx`)

Add a new `<Paper p="lg" shadow="xs">` below the existing FHIR server Paper.

Layout:

```
Terminology Server                      ← <Title order={3}>
  Server URL                            ← Text fw={600} size="sm"
  <Code>https://r4.ontoserver.csiro.au/fhir</Code>
  —or—
  <Text c="dimmed" size="sm">Not configured — set terminology.serverUrl in settings.yaml</Text>

  Status                                ← Text fw={600} size="sm"
  ● Reachable      (same dot component as sidebar, inline with label)

  [ Clear terminology cache ]           ← <Button variant="light" color="red" size="sm">
```

- Follows Phase 1's locked D-04 "file-only editing" pattern: URL is displayed with `<Code>`, NOT a form input. The only interactive control in this section is the Clear button.
- `<Title order={3}>` used to demote this section below the page's existing `<Title order={2}>Settings</Title>` heading. No change to the existing FHIR `<Paper>` above.
- Button icon: `<IconTrash size={16} />` (Tabler) in `leftSection`. No destructive modal — cache is locally rebuildable. Success feedback via `notifications.show({ color: 'green', title: 'Cache cleared', message: '...' })` (Mantine notifications already installed as required peer of @medplum/react).

### C-3: Resolved CodeableConcept rendering (Explorer HumanReadableView + ClinicalRawView)

No visible component change. Progressive enhancement per D-12:

1. First render: resource handed to `<ResourceTable>` unmodified → Medplum renders raw code in any Coding that lacks `display` (native Medplum `formatCoding` fallback to `code`).
2. When `useResolvedResource()` settles: a new resource instance (with `Coding.display` populated) is passed to `<ResourceTable>`, which re-renders the text in place.
3. No spinner, no skeleton, no fade, no layout reservation beyond Medplum's default line-height. The text swap is atomic and the row height does not change (display strings and raw codes both render as single-line `<td>` content; Medplum already uses `word-break: break-word`).
4. If resolution fails or times out, the raw code remains displayed. No toast, no tooltip in v1.

**Visual contract for unresolved display:** when the Coding has no `display` after enrichment completes, Medplum renders `coding.code`. The planner MUST render this fallback through a lightweight wrapper that outputs the code inside `<Code>` (Mantine) when no display is present. This wrapper is phase-scoped — inject it only at our enrichment boundary, do not fork Medplum internals. Concretely: the `<ResolvedResource>` wrapper copies the resource, and for any Coding where resolution failed (negative cache hit), it sets `coding.display = `…`${coding.system}|${coding.code}`…` ` — no. Revised: do NOT inject pseudo-display. Leave `display` unset so Medplum's native fallback emits the plain `code` string. The monospace/gray treatment applies only where we explicitly render codes ourselves (e.g., if Phase 5 introduces a "raw codes" column). For Phase 4, Medplum's native rendering is accepted as-is and no `<Code>` wrapper is applied inside `ResourceTable`.

**This simplification is intentional:** progressive enhancement per D-12 means users see identical visual treatment whether the code is resolved or not — only the text differs. The "unresolved code" signal is deferred until a Phase 5 UX review, consistent with D-07's "subtle" wording.

### C-4: Resolved CodeableConcept in SearchControl table rows

Out of scope for Phase 4 per D-09 (documented limitation). No UI contract — SearchControl continues to render raw codes in table cells. A future phase adds row-level resolution.

## Interaction Contracts

| Interaction | Trigger | Feedback | Error state |
|-------------|---------|----------|-------------|
| Terminology health probe on app connect | `ConnectionProvider` → successful FHIR connect fires parallel terminology `metadata` fetch with 3s timeout | Sidebar second row updates from `Checking…` → `Reachable` / `Unreachable` / `Not configured` | Silent. Failure renders `● Terminology: Unreachable`. No toast. No retry button in v1. |
| Clear terminology cache | User clicks `Clear terminology cache` button in Settings | Button is enabled immediately, action is synchronous (Map.clear + localStorage.removeItem). Mantine `notifications.show` toast appears with green checkmark, auto-dismisses in 4s. Button remains enabled (no lockout) — re-clicking with empty cache shows the `No cached terms to clear.` variant. | N/A — clearing a Map cannot fail in practice. If localStorage write throws (private mode / quota), silently swallow and still show toast (Map was cleared regardless). |
| CodeableConcept resolution (passive) | Any rendered Resource containing Codings | Text swap happens on resolver settle. No spinner per D-12. No layout shift. | Silent fallback to raw `code`. |

## Accessibility Contract

- Sidebar status rows: color dot + text label. Do not rely on color alone — label text carries the full state information. Labels use `c="dimmed"` (Mantine's dimmed gray is 4.5:1+ on white background). No aria-live announcement in v1 (status changes are low-frequency and color+text is redundant).
- Clear cache button: standard Mantine `<Button>` — keyboard accessible, focus ring preserved. Toast uses Mantine notifications default role (`status` / polite).
- Progressive-enhancement text swap: no ARIA live region. The swap is a visual refinement, not a state change the user acts on.

## Cross-View Consistency

Resolution must feel identical across HumanReadableView and ClinicalRawView because both render the same `<ResourceTable value={resource}>`. The enrichment happens upstream (`useResolvedResource`) so the visual contract applies wherever that hook is used. The ClinicalRawView's right-hand JSON pane shows the original (unenriched) resource so developers can see the wire-format values; this is intentional and matches the "clinical vs raw" split already established in Phase 2 D-10.

DeveloperJsonView is NOT wrapped with `useResolvedResource` — it always shows wire-format JSON.
