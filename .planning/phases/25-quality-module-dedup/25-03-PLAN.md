### DrillDownShell signature (QDDEP-02)

```typescript
// src/components/quality/DrillDownShell.tsx
import type { AsyncRunStatus } from '../../hooks/internal/asyncRunReducer';
import type { NormalizedIssue } from '../../quality/types'; // or wherever NormalizedIssue lives

export interface DrillDownShellProps {
  /** Drill-down title text shown in the header (e.g., `${type} — Plausibility drill-down`). */
  title: string;
  /** Back link href (always '/quality' today; left explicit for future flexibility). */
  backHref: string;
  /** Full run state object (status + progress), matching RunProgress's prop shape. */
  run: { status: AsyncRunStatus; progress: { current: number; total: number } };
  /** Normalized issues to render in the issues table. Pass [] if drill-down has a bespoke body (see CodingDrillDown). */
  issues: NormalizedIssue[];
  /** Error message to display when run.status === 'error'. */
  errorMessage?: string;
  /** Empty-state text shown when run.status === 'complete' and issues.length === 0. */
  emptyMessage: string;

  // OPTIONAL 7th prop — see PLANNER BRIEF below for rationale; NOT counted against the ≤6 required-props cap.
  /** Text prefix for the running-state progress label (e.g., "Checking", "Matching patients"). Default: "Running". */
  progressLabel?: string;
}

export function DrillDownShell(props: DrillDownShellProps): JSX.Element;
```

### 7th-prop justification (planner-brief approved)

CONTEXT.md D-05 specifies "props interface ≤ 6 fields" for REQUIRED props. The 5 simple drill-downs vary the running-state progress text ("Checking {type}", "Matching patients", "Checking references in {type}", etc.) — per RESEARCH.md Focus Area 2, this variation cannot be collapsed into `title` without forcing drill-downs to interpolate display-only text into a semantically-different field.

**Decision (per planner brief):** Add `progressLabel?: string` as a 7th OPTIONAL prop. The ≤6 cap is preserved for REQUIRED props (title, backHref, run, issues, emptyMessage are the required 5; errorMessage is optional, so the required count is 5). The 7th `progressLabel` is optional and defaults to "Running" — uniformity preserved when not specified. Count of required props: 5 ≤ 6 ✓.

**Alternative considered and rejected:** Fold the label into `title`. Rejected because the title is persistent ("Plausibility drill-down") and the progress label is ephemeral ("Checking {type}") — merging them would show "Plausibility drill-down — Checking Observation" permanently, which is wrong DOM.

### Rendering contract

`DrillDownShell` renders:
```tsx
<Stack p="xl" gap="md">
  <Button component={Link} to={backHref} variant="subtle" leftSection={<IconArrowLeft/>} ref={backRef}>
    Back
  </Button>
  <Title order={2}>{title}</Title>
  <RunProgress run={run} label={progressLabel ?? 'Running'} />
  {run.status === 'error' && (
    <Alert color="red" icon={<IconAlertTriangle/>}>
      {errorMessage ?? 'Unknown error'}
    </Alert>
  )}
  {run.status === 'complete' && issues.length === 0 && (
    <Alert color="green" icon={<IconCheck/>}>
      {emptyMessage}
    </Alert>
  )}
  {(run.status === 'complete' || run.status === 'cancelled') && issues.length > 0 && (
    <ResourceIssueTable issues={issues} />
  )}
</Stack>
```

### PARTIAL-migration composition — CodingDrillDown (CRITICAL — planner brief approved)

CodingDrillDown has 270 LOC today. Per D-07, it is a PARTIAL migration: chrome (back, title, status, progress, error) folds into the shell; the bespoke per-path coverage body does NOT.

**COMMITTED composition approach (this plan):** "issues=[] + sibling body".

Concretely, CodingDrillDown's return body changes from:

```tsx

  <Button .../>Back</Button>
  <Title>{type} — Coding coverage breakdown</Title>
  {state === 'loading' && <Text>Loading...</Text>}
```

```tsx
<Stack p="xl" gap="md">

    title={`${type} — Coding coverage breakdown`}
    backHref="/quality"
    run={syntheticRun}
    issues={[]}
    errorMessage={errorMessage}
    emptyMessage="No coded fields in sample"
  />
  {coverageReport && coverageReport.totalCodedFields > 0 && (
    <BespokePerPathCoverageTree
      report={coverageReport}
      /* reads coverageReport.perPathExamples — from Plan 25-01 */

```

**Rationale:**
- Shell renders chrome WITH empty issues array (so the "No issues found" green alert only fires if `totalCodedFields === 0`; executor checks the current CodingDrillDown's semantic — if the empty state is "no coding data at all", pass `emptyMessage="No coded fields in sample"`; else pass something faithful to current behavior).
- Bespoke body is rendered as a sibling INSIDE the outer Stack. Shell's own inner Stack is a nested Stack — Mantine handles nested Stacks cleanly (gap accumulates), visual diff expected to be minimal. **If render-parity test catches a visible divergence, fix by wrapping the shell's body in a fragment rather than an inner Stack** — but keep Stack as the default for 5 simple drill-downs.
- The `syntheticRun` variable maps CodingDrillDown's current hook-driven `state` to an `AsyncRunStatus`:
  ```typescript
  const syntheticRun = useMemo<DrillDownShellProps['run']>(() => ({
    status: state === 'loading' ? 'running'

          : state === 'data'    ? 'complete'
          : 'idle',
    progress: { current: 0, total: 0 },  // no progress bar for coding — totalCodedFields isn't a running progress

  ```
  Because `progress.total === 0`, `RunProgress` inside the shell renders null for coding (verify: `status === 'running'` + `total === 0` should render null — if not, adjust RunProgress in Plan 25-02 to gate on `total > 0` as well; executor confirms during migration).

- CompletenessDrillDown has the SAME asymmetry (hook-driven state, no `AsyncRunStatus`). Apply the SAME `syntheticRun` helper pattern. Unlike coding, Completeness HAS a progress concept (sampled/total resources), so populate `progress` meaningfully IF the hook exposes it; else pass `{current: 0, total: 0}`.
