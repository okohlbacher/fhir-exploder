    - Given a capability with absent `rest` → returns `{}`. Given `rest: [{ resource: [] }]` → returns `{}`. Given `rest: [{ resource: [{ type: 'Encounter' }] }]` (no searchParam) → returns `{}`.

  <action>
    Create `src/utils/capabilityStatementCatalog.ts` exporting `buildDynamicCatalog(capability: CapabilityStatement): ReverseReferenceCatalog`. Import `CapabilityStatement` (type) from `@medplum/fhirtypes` and `ReverseReferenceCatalog`, `ReverseReferenceEntry` (types) from `./reverseReferenceCatalog`.

    Define a module-level `COMMON_REFERENCE_TARGETS = new Set([...])` containing these ~41 FHIR R4 resource-type names (PascalCase): Patient, Encounter, Practitioner, Organization, Location, Medication, Device, Observation, Condition, Procedure, Immunization, AllergyIntolerance, DiagnosticReport, ImagingStudy, ServiceRequest, CarePlan, CareTeam, Goal, Consent, MedicationRequest, MedicationStatement, MedicationDispense, Coverage, Claim, ClaimResponse, Provenance, RelatedPerson, Specimen, BodyStructure, DocumentReference, Composition, Communication, Task, Appointment, Schedule, Slot, PractitionerRole, HealthcareService, Endpoint, Group, List.

    Add a private `capitalize(s: string): string` that upper-cases the first character (`"patient"` → `"Patient"`), returning `s` unchanged when empty.

    Algorithm (per RESEARCH Finding 2): read `const resources = capability.rest?.[0]?.resource ?? []`. For each `resource`, skip if `!resource.type`. For each `sp` in `resource.searchParam ?? []`, skip if `sp.type !== 'reference'` or `!sp.name`. Compute `targetType = capitalize(sp.name)`; skip if `!COMMON_REFERENCE_TARGETS.has(targetType)`. Otherwise `catalog[targetType] ??= []` and push `{ type: resource.type as ReverseReferenceEntry['type'], param: sp.name }`. Build into a mutable `Record<string, ReverseReferenceEntry[]>` and return it cast `as ReverseReferenceCatalog` (the allowlist filter makes the cast safe — see RESEARCH Finding 9).

    Constraints (RESEARCH Finding 10): NEVER throw — return `{}` on any empty/sparse input. Do NOT follow `sp.definition` URLs (REVR-DYN-EXT deferred — ignore the `definition` field entirely). Do NOT add a network call — the function receives an already-parsed object. Add a JSDoc block stating the return-`{}`-never-throw contract and the convention-based inference approach.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Blaze server → app | The `/metadata` CapabilityStatement is server-controlled untrusted JSON; its `rest[*].resource[*].searchParam` shapes are parsed into the dynamic catalog. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-60-01 | Tampering | buildDynamicCatalog parsing server CapabilityStatement | mitigate | Defensive access only (`rest?.[0]?.resource ?? []`, `resource.searchParam ?? []`); guard `!resource.type`/`!sp.name`; never throw; allowlist (COMMON_REFERENCE_TARGETS) filters param-name→type inference so arbitrary server-supplied param names cannot inject unknown resource types into the catalog. |
| T-60-02 | Denial of Service | connect() building catalog from a huge CapabilityStatement | accept | Catalog build is a single synchronous O(resources × searchParams) pass over an already-fetched, already-parsed object; no recursion, no network, no `definition` URL follow (REVR-DYN-EXT deferred). Worst case bounded by metadata size the client already loaded. Low-value local tool. |
| T-60-03 | Information Disclosure | dynamicCatalog stored in React connected state | accept | Catalog holds only resource-type names and search-param strings already visible in /metadata; no PII, no secrets. |
</threat_model>
