<objective>
Restore live-Blaze functionality of every per-patient resource search in `/patients/:id` views. Blaze 1.6.2 returns HTTP 400 `"Unknown search-param 'date' in sort clause."` whenever the URL includes `&_sort=-date`. The Phase 38 HUMAN-UAT walk proved this nukes (a) the entire Laborbefund tab (Test 1, Test 6 — UAT-FU-06 regression cascade), (b) the entire Zeitleiste timeline (Test 2 — MII-EXT-08 regression), and indirectly affects the `$everything` view (`PatientTimeline`) and the cross-resource view (`FhirResourcesView`) the same way. Curl probes confirmed `_sort=-_lastUpdated` is accepted by Blaze 1.6.2 universally.

Purpose: close the 3 critical-severity hits in `33-HUMAN-UAT.md` Tests 1, 2, 6 that Phase 38 surfaced; lock the regression so jsdom-mocked tests can never silently miss a Blaze sort-param incompatibility again; preserve the Phase 33 D-07 chronology semantics (newest-first ordering) — `_lastUpdated` approximates the original `date` ordering for Synthea-style bundles where resource creation time tracks clinical date.

Output: 4 swapped source files, 1 expanded test file with a locking assertion, the existing Vitest baseline still green, and (post-checkpoint) 3 Phase 33 HUMAN-UAT rows annotated with `→ fixed in Phase 38.1, commit <sha>` per Phase 38 D-03.

Scope discipline: this plan touches ONLY the 4 listed source files and 2 colocated test files (plus the HUMAN-UAT writeback after re-walk). It does NOT audit other `_sort=` usages elsewhere in the codebase, does NOT refactor sort logic into a shared helper, and does NOT touch Phase 33's verification narrative beyond the per-D-03 row append.
</objective>
