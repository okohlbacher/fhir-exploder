# Phase 36: Phase 34 profile lazy-load (bundle-size waiver follow-up) — Research

**Researched:** 2026-04-25
**Domain:** Vite dynamic-import + JSON code-splitting; FHIR StructureDefinition consumer wiring
**Confidence:** HIGH (codebase facts grep-verified; Vite/Vitest behavior triangulated against vendor docs and repo history)

## Summary

Phase 36 has two intertwined goals:
1. **Bundle-size:** Get the 224.73 KB gzipped `profiles-*.js` chunk OUT of the initial-load critical path. The chunk holds 483 trimmed MII extension StructureDefinition JSONs that are pulled in by 501 static `import` statements at the top of `src/quality/profiles/extensions/index.ts` (1008 lines, GENERATED by `scripts/fetch-mii-profiles.mjs`).
2. **Wire a real consumer:** The current production helpers `getExtensionProfileForUrl(url)` and `BUNDLED_EXTENSION_PROFILE_URLS` (`src/quality/profiles/index.ts:58-66`) have ZERO callers. v1.5 audit flagged this as an orphaned export (`v1.5-MILESTONE-AUDIT.md:160-167`).

The two problems share one mechanism: the consumer must look up profiles by `meta.profile[*]` URL (NOT by resource type), because each MII extension package ships multiple SDs of the same FHIR type (Onkologie alone has 7+ Condition profiles). Because lookups are URL-keyed, lazy-loading via per-URL `import()` is a natural fit.

**Primary recommendation:** Use `import.meta.glob('./*.json', { import: 'default' })` (lazy variant — no `eager: true`) to register every JSON file at build time as a `() => Promise<StructureDefinition>` thunk, then resolve URL→filename on first access by importing each file once and caching by URL in a module-scoped `Map`. Wire the consumer into `profileConformanceChecker.ts` via a new `useExtensionConformanceCheck` step in `useConformanceRun.ts` that reads `resource.meta.profile[*]`, awaits `getExtensionProfileForUrl(url)`, and feeds the resolved SD into `validateConformance(...)`. This keeps the existing eager `getProfileForType(resourceType)` path untouched (back-compat) and wraps async-only on the extension code path.

### Pattern 1: URL-keyed dynamic-import map (RECOMMENDED — emitted by `fetch-mii-profiles.mjs`)
**What:** Replace the 501 static `import sdN from './X.json'` lines + 501-entry `REGISTRY` literal in `extensions/index.ts` with a single object literal whose values are `() => import('./X.json')` thunks. Vite chunks each dynamic import into its own asset (or into shared chunks per its grouping heuristic). The KEY in the literal is the canonical SD URL — known to the fetch script at emit time because it parsed the SD already.

**When to use:** All cases. This is the production path for Phase 36.

**Code shape (post-refactor `extensions/index.ts`):**
```typescript
// GENERATED by scripts/fetch-mii-profiles.mjs — DO NOT EDIT BY HAND.
// Regenerated on npm install via the 'prepare' lifecycle hook.
import type { StructureDefinition } from '@medplum/fhirtypes';

// Each value is a thunk that triggers a per-file dynamic import.
// Vite splits each `import('./X.json')` into its own chunk (or groups
// them) so the 277 KB gz extension payload is OUT of the initial bundle.
//
// Returns a Promise<{ default: SD }> per Vite/Rollup convention; callers
// must read `.default`. See Pitfall 1.
type LazyProfile = () => Promise<{ default: StructureDefinition }>;

export const REGISTRY: Record<string, LazyProfile> = {
  'https://www.medizininformatik-initiative.de/fhir/ext/modul-bildgebung/StructureDefinition/mii-ex-bildgebung-bildgebungsgrund':
    () => import('./Extension-mii-ex-bildgebung-bildgebungsgrund.json') as Promise<{ default: StructureDefinition }>,
  // ... 483 entries
};
```

The fetch script knows both `sd.url` and `filename` inside its loop (`scripts/fetch-mii-profiles.mjs:152-167`), so this is a one-line change to the emit:
```javascript
// OLD (line ~166):
registryLines.push(`  [(${varName} as unknown as StructureDefinition).url]: ${varName} as unknown as StructureDefinition,`);

// NEW (no varName needed; key is sd.url; value is a thunk):
registryLines.push(`  ${JSON.stringify(sd.url)}: () => import('./${filename}') as Promise<{ default: StructureDefinition }>,`);
// (also: drop the static import line emission entirely)
```

### Pattern 2: Async memoizing wrapper in `src/quality/profiles/index.ts`
**What:** Convert `getExtensionProfileForUrl` from sync `→ SD | null` to async `→ Promise<SD | null>`. Cache resolved SDs in a module-scoped `Map<string, StructureDefinition>` so each canonical URL pays the lazy-import cost exactly once per session. In-flight requests must also be deduplicated (concurrent calls for the same URL share the same Promise) to avoid double-fetch under React StrictMode.

**Code shape:**
```typescript
// src/quality/profiles/index.ts (replaces lines 56-66)
import { REGISTRY as EXTENSION_REGISTRY } from './extensions/index';

export const BUNDLED_EXTENSION_PROFILE_URLS = Object.keys(
  EXTENSION_REGISTRY,
) as readonly string[];

const extensionProfileCache = new Map<string, StructureDefinition>();
const extensionProfileInFlight = new Map<string, Promise<StructureDefinition | null>>();

export async function getExtensionProfileForUrl(
  canonicalUrl: string,
): Promise<StructureDefinition | null> {
  const cached = extensionProfileCache.get(canonicalUrl);
  if (cached !== undefined) return cached;

  const inFlight = extensionProfileInFlight.get(canonicalUrl);
  if (inFlight !== undefined) return inFlight;

  const loader = EXTENSION_REGISTRY[canonicalUrl];
  if (!loader) return null;

  const promise = loader().then((mod) => {
    const sd = mod.default;
    extensionProfileCache.set(canonicalUrl, sd);
    extensionProfileInFlight.delete(canonicalUrl);
    return sd;
  }).catch((err) => {
    extensionProfileInFlight.delete(canonicalUrl);
    // Surface failure as null per ROADMAP: "load on-demand" semantics; logging
    // happens at the caller boundary.
    console.warn(`[extensions] failed to lazy-load ${canonicalUrl}: ${err}`);
    return null;
  });
  extensionProfileInFlight.set(canonicalUrl, promise);
  return promise;
}
```

### Pattern 3: Production consumer in `useConformanceRun.ts`
**What:** Add a step between "Step 2: Get profile" and "Step 3: Expand value sets" that reads `meta.profile[*]` from each sampled resource, awaits the extension SDs in parallel via `Promise.all`, and feeds them into `validateConformance` alongside the base profile. This wires `getExtensionProfileForUrl` to a real code path AND extends conformance coverage to the extension profiles already shipping in the bundle.

**Where:** `src/hooks/useConformanceRun.ts:173` (`const profile = getProfileForType(resourceType);`). Already inside an async IIFE (`void (async () => {`) so awaiting is free.

**Code shape (insertion after line 173):**
```typescript
// Step 2b (Phase 36 / MII-EXT-12 lazy-load consumer): collect canonical URLs
// from meta.profile[*] across the sampled resources and lazy-load the matching
// extension SDs. Failed loads silently skip — extension validation is best-effort.
const extensionUrls = new Set<string>();
for (const r of sample) {
  const profiles = (r as { meta?: { profile?: string[] } }).meta?.profile;
  if (Array.isArray(profiles)) {
    for (const url of profiles) {
      if (BUNDLED_EXTENSION_PROFILE_URLS.includes(url)) {
        extensionUrls.add(url);
      }
    }
  }
}
const extensionProfilesByUrl = new Map<string, StructureDefinition>();
if (extensionUrls.size > 0) {
  const results = await Promise.all(
    Array.from(extensionUrls).map(async (url) => {
      const sd = await getExtensionProfileForUrl(url);
      return [url, sd] as const;
    }),
  );
  for (const [url, sd] of results) {
    if (sd) extensionProfilesByUrl.set(url, sd);
  }
}
```

Then inside the validation loop (around line ~225), in addition to `validateConformance(resource, profile, expandedValueSets)`, also iterate `resource.meta.profile` and call `validateConformance(resource, extensionProfilesByUrl.get(url), expandedValueSets)` for each matching extension SD. Issues fold into the same `batchConformanceIssues` array.

**Why this site:** `useConformanceRun` is (a) already async, (b) already iterates a sample and reads each resource's metadata, (c) already calls `validateConformance` once per resource — a natural extension. The alternative site `validationBackends.ts::createConformanceBackend` (line 54) takes a SYNC `getProfile` callback in its closure, so wiring async there requires either eager-pre-resolving the URLs into a `Map` before constructing the backend (same shape as Pattern 3 but in a different file) OR turning the backend's `getProfile` arg into async (cascading change). Pattern 3 keeps async confined.

### Anti-Patterns to Avoid
- **`import.meta.glob` lazy variant for the canonical-URL key:** Glob discovers files at build time but the URL is INSIDE the JSON — to populate the URL→thunk map you'd have to import every file just to read `.url`, defeating laziness. **Use the hand-written map** emitted by the fetch script (which knows the URL at emit time).
- **Forgetting `.default` on dynamic JSON imports:** `await import('./foo.json')` returns `{ default: <jsonContent> }` — NOT the JSON directly. Static imports `import x from './foo.json'` look identical but Vite's static-JSON transform handles the unwrap automatically. See Pitfall 1.
- **Sync API surface for an async operation:** Don't keep `getExtensionProfileForUrl` returning `SD | null` and "secretly" cache after first call (e.g., kick off load on import). Pre-warming hides the latency from the user but creates surprising race conditions in tests. Make it explicitly `Promise<SD | null>` and force the consumer to await.
- **Double-loading via React StrictMode:** Without in-flight deduplication (Pattern 2), the second StrictMode invocation kicks off a second `import()` for the same URL. Vite's chunk loader deduplicates network requests at the browser level but the parse+cache work doubles. The `extensionProfileInFlight` Map fixes this.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Discover JSON files at build time | A node script that reads the directory and writes a manifest | The fetch script `scripts/fetch-mii-profiles.mjs` already iterates the SDs — reuse its loop. | One source of truth; the script already produces `index.ts`. |
| Track URL → filename mapping | Read each JSON to extract `.url` at runtime | Emit URL as the key in `extensions/index.ts` from the fetch script (it already has `sd.url` in scope at line 152). | URL is known at script-emit time; capturing it eliminates the runtime "load to discover URL" antipattern. |
| Deduplicate concurrent dynamic imports | Custom Promise-tracking infrastructure | Module-scoped `Map<url, Promise<SD|null>>` with a single get-or-set check. | Standard React hook idiom; no library needed. |
| Visualize bundle size | Custom `du -sh dist/assets/*.gz` wrappers | `rollup-plugin-visualizer` (already installed; gated on `ANALYZE=1`). | Already wired in `vite.config.ts:11-21`. |

**Key insight:** The hardest part of this refactor is NOT the lazy-load mechanics — it's resisting the urge to bury the asynchrony deeper. Make `getExtensionProfileForUrl` honestly `async` and wire it into the one consumer that's already async (`useConformanceRun`). Trying to keep the public API sync forces module-init-time eager-load, which defeats the whole purpose.

## Common Pitfalls

### Pitfall 1: `await import('./foo.json')` returns `{ default: ... }`, NOT the SD directly
**What goes wrong:** `getExtensionProfileForUrl` returns `undefined` for every URL because the loader thunk's `await` produces `{ default: <SD> }` but the cache stores it whole, and downstream code reads `.url`/`.snapshot` and gets `undefined`.
**Why it happens:** Vite's static `import sd from './foo.json'` transform unwraps the default export at build time so `sd` is the JSON. Dynamic `import()` does not — it follows the spec ESM module-namespace shape. [CITED: vitejs/vite Discussion #3509 + Issue #11359 — confirmed 2026-04-25 via WebSearch]
**How to avoid:** Always read `mod.default` in the loader chain (Pattern 2 does this). Type the thunk as `() => Promise<{ default: StructureDefinition }>` so TypeScript catches a missing `.default` access. Add a unit test that asserts `(await getExtensionProfileForUrl(url))!.url === url`.
**Warning signs:** TypeScript error "Property 'url' does not exist on type '{ default: StructureDefinition }'"; runtime error "cannot read properties of undefined (reading 'url')".

### Pitfall 2: Vite chunk-grouping defeats per-file splitting
**What goes wrong:** With 483 dynamic imports of small JSON files, Vite/Rollup's default chunk-grouping heuristic may concatenate them all back into one big async chunk (e.g., `extensions-DEADBEEF.js`), because each file is tiny. The initial-bundle goal still hits (chunk is async-only) but the on-demand fetch downloads ALL profiles whenever ONE is needed.
**Why it happens:** Rollup minimizes HTTP request count by default; tiny imports are merged. Vite 8 / Rolldown's `build.rollupOptions.output.advancedChunks` and `manualChunks` give explicit control. [CITED: rollupjs.org configuration-options + Vite GitHub Issue #12209 — confirmed 2026-04-25 via WebSearch]
**How to avoid:**
- After Step 6 (`ANALYZE=1 npm run build`) inspect `visualizer-after.html`: if a single async `extensions-*.js` chunk holds all 483 files, the initial-load gate STILL passes (chunk is non-blocking) but on-demand fetch is sub-optimal. **Acceptable for Phase 36 — meets the gate.**
- If per-URL granularity is required for a v1.6 follow-up, set `build.rollupOptions.output.manualChunks` to assign one chunk per file or per MII module package (e.g., bildgebung-*.json → one chunk).
**Warning signs:** Treemap shows ONE big async chunk under the dynamic-imports section instead of N small chunks.

### Pitfall 3: React StrictMode double-invokes the lazy-load
**What goes wrong:** Without in-flight deduplication, StrictMode's second-render invocation calls `getExtensionProfileForUrl(url)` again before the first call resolves; both kick off `loader()`; module-record-cache hides the doubling but the extra Promise+`.then` chain creates spurious work and possible race conditions in tests using `vi.useFakeTimers()`.
**Why it happens:** Standard StrictMode invariant — every effect/render runs twice in dev. Browser-level chunk-loading deduplicates HTTP but JS-level call counts double.
**How to avoid:** `extensionProfileInFlight` Map (Pattern 2). Test with a `vi.fn` spy on a mocked `EXTENSION_REGISTRY[url]` thunk to assert it's called exactly once across two concurrent `getExtensionProfileForUrl(url)` invocations.
**Warning signs:** Test asserting "loader called 1×" fails with "called 2×" under StrictMode.

### Pitfall 4: `npm test` fails with empty `EXTENSION_REGISTRY` because `prepare` script didn't run
**What goes wrong:** Fresh clone with `--ignore-scripts` skips the `prepare` hook; `extensions/index.ts` was either never generated or generated with empty content; `BUNDLED_EXTENSION_PROFILE_URLS` is `[]`; tests asserting `(await getExtensionProfileForUrl(...))!.url === ...` fail with `null`.
**Why it happens:** The fetch script bails out without writing `index.ts` if all package fetches fail (defensive-early-return at `scripts/fetch-mii-profiles.mjs:182-188`), preserving committed JSON. But on a TRULY fresh clone the committed `index.ts` IS present (it's the source-of-truth offline fallback per CONTEXT D-12).
**How to avoid:**
- The committed `extensions/index.ts` IS the offline fallback — Phase 36 preserves this invariant by re-generating in the SAME defensive way. Keep the early-return at line 182.
- Phase 36 plan must include a verification step: after script edit, delete `extensions/index.ts`, re-run `npm install`, confirm regeneration produces a valid file with 483 thunks.
**Warning signs:** Tests fail in CI on "fresh checkout" workflows but pass locally.

### Pitfall 5: Async `getExtensionProfileForUrl` breaks any sync caller you missed
**What goes wrong:** The current API is sync (`SD | null`). Tooling helps catch all call sites — but a future PR adds a sync caller assuming the legacy contract; nothing fails at compile time because the new caller awaits a `Promise<SD | null>`, gets a Promise back, treats it as truthy, and accesses `.url` returning `undefined`.
**Why it happens:** TypeScript catches `await` omission only when the consumer types the variable as the awaited shape. Loose `any` or implicit-any in test scaffolding can hide this.
**How to avoid:**
- Grep verification before merge: `grep -rn 'getExtensionProfileForUrl' src/ | grep -v 'await getExtensionProfileForUrl'` should show zero non-await call sites (other than `BUNDLED_EXTENSION_PROFILE_URLS` definition and re-exports).
- Add `as Promise<StructureDefinition | null>` annotation on the return type explicitly so TS errors on `.url` access without `.then`/`await`.
**Warning signs:** Build passes but a downstream consumer reads `undefined.url` at runtime.

### Pitfall 6: Visualizer treemap totals don't match `find dist/assets -type f -exec gzip -9c {} \; | wc -c`
**What goes wrong:** Phase 34 `34-06-UAT.md:100` showed the treemap's reported gzip size and the disk gzip total disagreed by ~5 KB. The discrepancy is small but the planner should pick ONE measurement method and stick with it for before-after parity.
**Why it happens:** Visualizer reports gzip of the IN-MEMORY chunk text; on-disk asset gzip includes Vite's per-file metadata (sourcemap comments etc.).
**How to avoid:** Use the same `find dist/assets -type f \( -name "*.js" -o -name "*.css" \) -exec gzip -9c {} \; | wc -c` formula Phase 34 used (cited at `34-06-UAT.md:100`). Document in PLAN.
**Warning signs:** Treemap "Total gz" differs from disk-gzip total by >1 KB.
