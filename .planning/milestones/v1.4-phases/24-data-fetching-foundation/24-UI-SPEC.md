# Phase 24 — UI Design Contract

> Visual and interaction contract for Phase 24 **Data-Fetching Foundation**. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Phase UI Profile

**No-UI-surface phase.** Phase 24 is a data-layer / hooks refactor only. Per `24-CONTEXT.md §domain`:

> "No user-visible UI changes. No scope beyond the 4 requirements."

The four requirements (FOUND-01, FOUND-02, FOUND-03, FOUND-04) all refactor non-rendering code:

| Requirement | Target | User-visible change |
|-------------|--------|----------------------|
| FOUND-01 | `useResourceCounts` + module-scope `Map<serverUrl::type, count>` cache | None — consumer signature unchanged at `DashboardPage.tsx:77`, `ResourceTypeLanding.tsx:24`, `QualityOverviewPage.tsx:108`; mount behavior becomes faster (no re-fetch) but no pixels change |
| FOUND-02 | `metricsCache.ts` `Map<serverUrl, QualityMetricsCache>` registry with 2-entry LRU; `clearQualityMetricsCache(serverUrl)` wired into `SettingsPage.handleSave` | None — `CompletenessPanel`, `CodingCoveragePanel` see no signature change; the existing "Clear cache" button in `SettingsPage.tsx` continues to fire — Phase 24 only ADDS count-cache clearing alongside it |
| FOUND-03 | New `useAsyncRun<TIssue>` hook owning `{status, progress, errorMessage, cancel, run}`; 4 report hooks refactor to wrap it | None — `usePlausibilityReport`, `useLabRangesReport`, `useDuplicateReport`, `useReferenceReport` keep their typed return shapes and backward-compatible consumer APIs |
| FOUND-04 | `useResourceCounts.ts:29` `cancelledRef` → closure-scoped `let cancelled` | None — fixes a latent cancellation bug; no render-path change |

**UI-SPEC scope:** declare design-system inheritance, confirm no tokens change, and record the "Clear cache" button's unchanged visual contract. The checker dimensions PASS vacuously because Phase 24 introduces zero new surfaces; the auditor has nothing to audit.

This UI-SPEC is deliberately short. Full design tokens live in `21-UI-SPEC.md` and `22-UI-SPEC.md` (last amended); Phase 24 inherits them verbatim without redeclaration.

### S1 + S2 — "Clear cache" button + settings save (behavior-only extension)

**Existing visual contract (from prior phases, unchanged):**

| Attribute | Value |
|-----------|-------|
| Component | `<Button variant="default">` (Mantine 8) |
| Label | `Clear cache` (verbatim; do not alter) |
| Position | Settings page, adjacent to the server/terminology form row (existing placement unchanged) |
| Size | Mantine default (`size="sm"`) — unchanged |
| Icon | none today; **do NOT add one in Phase 24** |
| Loading state | none (operation is synchronous — in-memory Map clear + scoped localStorage keys) |
| Toast on success | inherited from prior phases if present; Phase 24 does not add a new toast |
| Toast on save (S2) | inherited from existing `setSettings` flow; Phase 24 does not add a new toast |

**Phase 24 behavior extension (wiring, not visual):**

1. `SettingsPage.handleSave` now additionally calls `clearQualityCountCache(serverUrl)` alongside the existing `clearQualityMetricsCache(serverUrl)` — both fire on every settings save (D-05).
2. The existing `Clear cache` button handler calls `clearQualityCountCache(serverUrl)` in addition to `clearQualityMetricsCache(serverUrl)` (D-03).
3. No copy change, no button added, no icon added, no toast added.

**If a toast is already emitted today on "Clear cache" or "Settings saved":** keep the existing title, message, and color verbatim. Phase 24 does not alter notification contracts.

Phase 24 adds **zero new interactive surfaces**. The "Clear cache" button's existing interaction contract is reused without modification:

| State | Visual | Behavior |
|-------|--------|----------|
| Default | Mantine `<Button variant="default">` | cursor: pointer on hover |

| Disabled | never disabled in this phase | — |

The 4 report hook refactors (`usePlausibilityReport`, `useLabRangesReport`, `useDuplicateReport`, `useReferenceReport`) preserve the consumer panel's existing state machine exactly:

| Status | Panel render (pre-refactor = post-refactor) |
|--------|---------------------------------------------|
| `idle` | "Run report" CTA visible; no progress / result rendered |
| `running` | Progress bar + `Cancel` button visible; CTA disabled |
| `cancelled` | Last partial result (if any) + "Run report" CTA re-enabled |
| `error` | `errorMessage` surfaced inline (existing copy preserved); "Run report" CTA re-enabled |
| `complete` | Result table + "Re-run" CTA |

**No panel markup is modified by Phase 24.** If a panel must be touched to consume the new hook API shape, the diff is type-only (e.g., `run.status` stays as the same discriminated-union string) — no JSX edits.

## Notifications Contract

**Zero new notifications.** Phase 24 must not add a new toast. In particular:

- Do NOT add a "Cache cleared" toast on `Clear cache` click (if one does not exist today, do not add one). If one exists today, preserve it verbatim (title, message, color, autoClose).
- Do NOT add a "Settings saved" toast at `handleSave`. If one exists today, preserve it verbatim.
- Do NOT emit any new toast from inside `useAsyncRun`, `metricsCache.ts`, or the count-cache module. Toasts remain the responsibility of consumer panels (via `@mantine/notifications`) if and when they already emit them.

Rationale: adding a toast would be a user-visible change, which contradicts `24-CONTEXT.md §domain`.
