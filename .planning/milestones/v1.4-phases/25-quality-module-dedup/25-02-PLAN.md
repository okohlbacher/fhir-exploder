### D-12 RE-INTERPRETATION (CRITICAL — documented here per planner brief)

**What CONTEXT.md D-12 says:** "`useSampleWalker<T>` wraps `useAsyncRun<T>` internally."

**What RESEARCH (Focus Area 3) proved structurally impossible:** `useAsyncRun` manages a SINGLE async run lifecycle. `useSampleWalker` must manage N parallel runs (concurrency=4 worker pool per resource type). Literal wrapping (calling `useAsyncRun` inside `useSampleWalker`) would either:
  (a) force a single-run model onto N-run orchestration, losing the pool, OR
  (b) call `useAsyncRun` in a `.map(type => useAsyncRun(...))` loop — violates Rules of Hooks.

**Re-interpretation this plan commits to (planner brief approved):**
> "useSampleWalker reuses the **cancellation invariant** established by useAsyncRun (closure-scoped `let cancelled`, NOT `cancelledRef`), but owns the worker-pool concurrency directly. It does NOT call `useAsyncRun` internally."

**Why this is faithful to D-12's intent:** D-12 was written alongside D-10 (which says "reuse Phase 24's `let cancelled` pattern"). D-12's "wraps" is best read as "reuses the cancellation primitive" — D-10 is the load-bearing word, not "wraps." The walker is its own primitive alongside `useAsyncRun`, not beneath it.

**What the executor MUST do:**
- Apply the closure-scoped `let cancelled = false;` pattern at the top of the effect body
- Reference refs only to hold cancellation HANDLES (functions), never flags (booleans) — matching Phase 24 FOUND-04 convention
- Do NOT import `useAsyncRun` into `useSampleWalker.ts`
- Do NOT invoke `useAsyncRun(...)` anywhere inside `useSampleWalker`
- Document this decision in a comment header citing Phase 24 FOUND-04 and RESEARCH.md Focus Area 3

<design>
## useSampleWalker design (committed)

Per D-12 re-interpretation above, `useSampleWalker` is a SIBLING primitive to `useAsyncRun`, NOT a wrapper. It owns:

1. **Debounced size input** — `useDebouncedValue(sampleSize, DEBOUNCE_MS)`
2. **Memoized keys** — `typesKey`, `patientIdsKey` (per Bug B pattern, 23-05-SUMMARY)
3. **State** — `Record<string, PerTypeReport<T>>` via `useState`
4. **Lifecycle effect** with:
   - Closure-scoped `let cancelled = false` (NOT `cancelledRef`)
   - Early exit if `!client || types.length === 0`
   - Cache instance resolution: `const cache = getQualityMetricsCache(serverUrl)`
   - Seed loop populating `initial: Record<string, PerTypeReport<T>>` from cache hits (status `'loading'` for misses)
   - Worker pool: `let active = 0; const queue = types.filter(t => initial[t] === 'loading')`
   - Recursive `next()` that invokes `args.compute(client, t, debouncedSize, patientIds)`, writes cache on success, dispatches `setReports`, respects `CONCURRENCY` limit
   - Cleanup: `return () => { cancelled = true }`
   - Deps: `[client, typesKey, debouncedSize, patientIdsKey]`
5. **Return**: `{ reports }`

Per-metric rollup (e.g., "mean completeness across types") STAYS in the wrapper hooks — they compute it from `walker.reports` via their own `useEffect` and push into `QualityMetricsContext`. This preserves the roadmap success criterion #3 explicitly.

## Wrapper shrink plan

`useCompletenessReport.ts` (167 → ~50 LOC):
- Imports: remove `useMemo`, `useState`, `useEffect`, debounce — keep only what rollup needs
- Body:
  1. `useSettings()` / `useMedplumContext()` — as before
  2. `const { reports } = useSampleWalker<PerTypeCompletenessReport>({ client, types, sampleSize, patientIds, compute: completenessComputeForType, metricNamespace: 'completeness' });`
  3. Rollup `useEffect` that reads `reports`, averages, pushes to `QualityMetricsContext`
  4. `return reports` (same public shape)

`useCodingCoverage.ts` (143 → ~45 LOC): identical pattern with `aggregateCoverage` in the compute callback.

**LOC target** (per must_haves): ≤ 60 each (research target is ≤ 30; 50% slack per planner brief). The comment density the plan allows is generous.

## RunProgress — zero-transformation drop-in at 9 sites

Because the prop is `run: { progress: { current, total }, status }` (the exact `useAsyncRun` result shape), each site collapses from:

```tsx
{run.status === 'running' && (
  <Stack gap="xs" aria-live="polite">
    <Text size="sm">Checking {type} ({run.progress.current}/{run.progress.total})...</Text>
    <Progress value={Math.round((run.progress.current / run.progress.total) * 100)} animated />
  </Stack>
)}
```

to:

```tsx
<RunProgress run={run} label={`Checking ${type}`} />
```

Each site loses ~5 LOC + 2-3 imports (`Stack`, `Text`, `Progress` already imported for other purposes in some files; executor evaluates per-file). The component itself handles the `status === 'running'` conditional internally and returns `null` otherwise — equivalent behavior.
