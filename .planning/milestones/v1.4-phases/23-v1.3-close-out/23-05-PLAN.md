<objective>
Fix the two code defects diagnosed in 23-HUMAN-UAT.md `root_cause` that caused T-6.3 A to fail UAT on live Blaze with a 139-patient cohort: quality dashboard numbers did not change when the user activated a matching cohort.

**Bug A (OverviewStrip tiles unscoped):** `useResourceCountsMetrics` / `useResourceCounts` accept no patientIds argument, so OverviewStrip tiles 1-2 (`Total resources`, `Resource types`) always display server-wide counts — even when a cohort is active.

**Bug B (stale report results):** `usePlausibilityReport`, `useLabRangesReport`, `useDuplicateReport`, `useReferenceReport` call `useAsyncRun` without `autoStart: true`. When a cohort activates, their `patientIds` dep changes but the runner never re-fires because the `autoStart` gate at `useAsyncRun.ts:138-146` is `false`. Previously-computed unscoped results persist stale.

Completeness, Coding, and Validation already re-scope correctly (evidence: `useCompletenessReport.ts:73,119`; `useCodingCoverage.ts:64,112`; `useValidationRun.ts:172`) — this plan mirrors those patterns. A regression-guard smoke test on `useValidationRun` is included to catch silent regressions on the Validation tile.

**Chosen fix for Bug A:** plumb `patientIds` through `useResourceCounts` + `useResourceCountsMetrics` (scoped counts, matches UAT expectation) — NOT the degraded-UX alternative of labelling tiles "Server total (unscoped)".

**Chosen fix for Bug B:** `autoStart: true` with careful memoization, mirroring `useCompletenessReport.ts:119` (`patientIdsKey` useMemo on sorted-join) — NOT a manual `cancel()+reset` effect, because the primitive already owns that lifecycle via the autoStart effect's cleanup (`useAsyncRun.ts:142-144`).

Purpose: flip T-6.3 A UAT from `issue` to `pass` on re-run, unblocking Phase 23 close-out and the CLOSE-07 Nyquist flip.
Output: 7 modified source/test files, 6 new/extended test files (5 for Bug A/B + 1 Validation regression guard), 1 vitest run green.
</objective>
