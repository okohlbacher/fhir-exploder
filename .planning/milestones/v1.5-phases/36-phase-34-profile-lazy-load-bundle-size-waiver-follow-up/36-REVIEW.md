# Phase 36: Code Review Report

**Reviewed:** 2026-04-26
**Depth:** standard
**Files Reviewed:** 6
**Status:** issues_found

## Summary

Phase 36 refactors the MII extension-profile registry from 501 eager static imports
to URL-keyed lazy thunks (`() => import('./X.json')`) and wires
`getExtensionProfileForUrl` into the `useConformanceRun` Step 2b path. The
implementation is well-architected: the cache + in-flight Map pattern is the
correct shape for StrictMode-safe dedup, the codegen script defends against
empty/offline runs by preserving the committed registry, and the consumer
correctly memoizes lookups per-run. The `BUNDLED_EXTENSION_PROFILE_URLS`
export uses `Object.keys` which works for plain Records, and the test suite
exercises the dedup invariant explicitly with `vi.resetModules()`.

Findings center on (1) a real `O(n*m)` lookup cost in the consumer that's
also a correctness concern when `BUNDLED_EXTENSION_PROFILE_URLS` grows past
~480 entries, (2) abort-signal not propagating into in-flight extension
loads (orphaned promises mutate module-scoped state after unmount in
StrictMode), (3) a path-traversal class concern in the codegen script's
filename derivation from upstream `sd.url`/`sd.name`, and (4) several
quality items around code duplication, magic numbers, and a misleading
comment in the consumer test.

No Critical issues. The four Warnings should be addressed before this ships
to production users; the Info items are housekeeping.

## Warnings

### WR-01: O(n) Array.includes() lookup against ~480-entry URL list, called per resource per run

**File:** `src/hooks/useConformanceRun.ts:190`
**Issue:** `BUNDLED_EXTENSION_PROFILE_URLS.includes(url)` is invoked inside
a doubly-nested loop (outer over sampled resources, inner over each
resource's `meta.profile[]`). The list has ~481 entries (per
`extensions/index.ts` thunk count), and `Array.prototype.includes` is `O(n)`.
For a sample size of 1000 resources where each carries ~3 profile URLs in
`meta.profile[]`, this is ~1.44M string comparisons per run — measurable
overhead in the synchronous render path before the actual lazy-load even
starts. More importantly, this is unnecessary: the registry is a `Record`
whose own keys ARE the bundled URLs, so an `O(1)` lookup is available.
Also, `BUNDLED_EXTENSION_PROFILE_URLS` was generated by `Object.keys(REGISTRY)`
in `profiles/index.ts:63-65` only to feed this `includes()` check; replacing
the check eliminates the array entirely (or keeps it as a debug export).
**Fix:**
```ts
// In src/quality/profiles/index.ts — expose a Set alongside the array
export const BUNDLED_EXTENSION_PROFILE_URL_SET = new Set(
  Object.keys(EXTENSION_REGISTRY),
);

// In src/hooks/useConformanceRun.ts:190
import { BUNDLED_EXTENSION_PROFILE_URL_SET } from '../quality/profiles';
// ...
if (BUNDLED_EXTENSION_PROFILE_URL_SET.has(url)) {
  extensionUrls.add(url);
}
```
Alternative: skip the membership check entirely and let
`getExtensionProfileForUrl` short-circuit unknown URLs (it already returns
`null` for missing keys at line 83). The pre-filter exists only to avoid
launching ~N async no-ops, which is cheap enough that the simpler code may
win.

### WR-02: AbortController is not propagated to in-flight extension loads — orphaned promises mutate module-scoped cache after unmount

**File:** `src/hooks/useConformanceRun.ts:197-207`, `src/quality/profiles/index.ts:73-105`
**Issue:** `useConformanceRun` already wires an `AbortController` for the
cascade fetches (D-20, lines 130, 162, 401-408). But the lazy extension
loads at lines 197-207 are launched as bare `await getExtensionProfileForUrl(url)`
with no abort wiring. Two consequences:
1. **StrictMode double-mount edge case:** in dev, the unmount fires
   immediately after the first mount. The first mount's
   `getExtensionProfileForUrl` call writes to `extensionProfileInFlight` /
   `extensionProfileCache` (module-scoped, lines 67-71 of `profiles/index.ts`)
   AFTER the hook unmounts. This is fine for the cache (it's append-only and
   keyed by URL, so the second mount benefits) but it means
   `cancelledRef.current = true` doesn't actually cancel the network/disk
   work — it just suppresses the resulting state set. For 481 packages, that's
   acceptable; for offline mode where all fetches are local JSON, even better.
   But the contract claimed at line 51 of `profiles/index.ts` ("StrictMode-safe")
   refers ONLY to dedup, not to cancellation. A reader may expect the latter.
2. **Real-world risk:** if a future enhancement makes `loader()` slow (e.g.
   network-fetched JSON instead of bundled), the orphaned promises from a
   cancelled run will still resolve and call `extensionProfileCache.set(...)`
   on data the user no longer needs. Memory grows; no correctness bug today.

**Fix:** Either (a) document explicitly that the cache is module-scoped and
intentionally outlives mounts, or (b) make the `getExtensionProfileForUrl`
caller race the load against the abort signal:
```ts
// In useConformanceRun.ts:197-207
const ac = abortRef.current;
const results = await Promise.all(
  Array.from(extensionUrls).map(async (url) => {
    const sd = await getExtensionProfileForUrl(url);
    if (ac.signal.aborted) return [url, null] as const;
    return [url, sd] as const;
  }),
);
```
This doesn't stop the load, but it stops the consumer from acting on it.
Pair with a comment in `profiles/index.ts` documenting that the
module-scoped cache is intentional and survives unmounts.

### WR-03: Path-traversal / file-write class concern in `fetch-mii-profiles.mjs` filename derivation

**File:** `scripts/fetch-mii-profiles.mjs:155-166`
**Issue:** `filename` is built from `${typeSlug}-${slug}.json` where:
- `typeSlug = String(sd.type ?? 'Unknown').replace(/[^A-Za-z0-9]+/g, '')` —
  this strips slashes and dots, so it's safe.
- `slug = slugify(sd.name ?? sd.id ?? sd.url?.split('/').pop() ?? 'unknown')`
  — `slugify` is also alphanumeric-only with hyphens, also safe.

So the immediate path-traversal vector is closed. **However**, `sd.url` is
also embedded **verbatim** as both the registry key (line 176) and as a
JSON-stringified value in the emitted TS source (line 177). The script
trusts `sd.url` from upstream packages. If a future malicious or
accidentally-malformed package shipped an `sd.url` containing `"\n` or
` `/` ` or a closing `*/`, `JSON.stringify` would correctly
escape `"` and `\n`, but the resulting string is then **concatenated into
TypeScript source** — a context where `JSON.stringify` does NOT guarantee
safe escaping. Specifically:
- U+2028 / U+2029 are valid in JSON but illegal in JS string literals
  pre-ES2019; under modern targets, fine, but the emitted code's TS parse
  still depends on this assumption.
- An `sd.url` containing `*/` would pass through `JSON.stringify` as
  `"*/"` (no escaping), but since the emitted line uses double-quoted
  strings, this only matters if you were inside a `/* ... */` block. This
  generator emits no block comments around values, so it's safe **today**.
- More concerningly, an `sd.url` containing arbitrary content could be
  used to break out of the string and inject TS — but since
  `JSON.stringify` escapes `"`, `\`, and control chars, and the result is
  used as a string-literal value (not a property name with template
  injection), this is safe for well-formed JSON inputs.

The real risk is **future maintenance**: someone editing this generator to
also write `sd.name` or `sd.description` into a comment block could
trivially introduce TS-source injection. The current comment block on
lines 167-174 is hard-coded (good), but no guard rails prevent regressions.

**Fix:** Add a sanitization helper for any upstream-derived string written
into the generated TS, even if today's code paths happen to be safe:
```js
function safeForTsString(s) {
  // JSON.stringify handles ", \, control chars. We additionally reject
  // U+2028/2029 (legal JSON, illegal pre-ES2019 JS literals) and assert
  // the input is a string.
  if (typeof s !== 'string') throw new Error(`expected string, got ${typeof s}`);
  if (/[  ]/.test(s)) throw new Error(`illegal char in URL: ${s}`);
  return JSON.stringify(s);
}
// Then at line 177:
'  ' + safeForTsString(sd.url) + ": () => import(" + safeForTsString('./' + filename) + ")...,"
```
Also assert `sd.url.startsWith('http')` to reject any clearly malformed
canonical URLs early.

### WR-04: `extensionProfileCache` and `extensionProfileInFlight` Maps are module-scoped and never cleared — test isolation hazard

**File:** `src/quality/profiles/index.ts:67-71`
**Issue:** Both Maps are top-level module state. The test in
`extensionProfile.test.ts:95` relies on `vi.resetModules()` to get a fresh
module and bypass cache hits from earlier tests in the same file (test 5
explicitly calls this out). But:
1. **Cross-file test pollution:** any other vitest file in the same worker
   process that imports `quality/profiles` will share module state if
   vitest's default module isolation is overridden (e.g., by `vi.mock` calls
   that hoist). The current test in `conformance-run-extension-profiles.test.tsx`
   mocks `../quality/profiles` entirely, so it's safe — but a future test
   that imports the real module after this one runs may see stale entries.
2. **No reset API:** there is no exported function to clear the cache,
   which would normally be used by HMR or by a long-lived dev server that
   wants to re-fetch profiles after the JSON is regenerated. Today this is
   a non-issue because thunks resolve from compiled chunks, not from disk
   at runtime — but it's worth documenting.
3. **Promise rejection cleanup is incomplete:** the `.catch` at line 94-102
   deletes the in-flight entry and returns `null`, but the cache itself is
   never populated with the `null` result. So a transient failure (which
   shouldn't happen for bundled JSON, but could in dev with a malformed
   import) will be retried on every subsequent call. For 481 entries that's
   not catastrophic, but it differs from the comment's "subsequent calls
   hit the module-scoped cache" promise.
**Fix:** Either (a) export a `__resetExtensionProfileCacheForTesting()`
function guarded by a `process.env.NODE_ENV !== 'production'` check, or
(b) decide that null results should also be cached (memoize failures) and
update both the cache check at line 76-77 and the `.catch` at line 94 to
write `null` into the cache:
```ts
// Option (b): cache failures too
.catch((err) => {
  extensionProfileInFlight.delete(canonicalUrl);
  extensionProfileCache.set(canonicalUrl, null as unknown as StructureDefinition);
  // ... log ...
  return null;
});
```
Note the type-cast required because `extensionProfileCache` is currently
`Map<string, StructureDefinition>`; widen to `Map<string, StructureDefinition | null>`
and update the cache-hit check accordingly:
```ts
if (extensionProfileCache.has(canonicalUrl)) {
  return extensionProfileCache.get(canonicalUrl) ?? null;
}
```

## Info

### IN-01: `BUNDLED_PROFILE_TYPES` and `BUNDLED_EXTENSION_PROFILE_URLS` cast `Object.keys()` to `readonly string[]`

**File:** `src/quality/profiles/index.ts:39, 63-65`
**Issue:** `Object.keys()` returns `string[]`, but `as readonly string[]`
casts away the mutability without changing the runtime type. Callers of
`BUNDLED_EXTENSION_PROFILE_URLS` could still mutate it via `.push`,
`.splice`, etc. (e.g., `WR-01`'s alternative uses `.includes` — readonly
in TS, but a malicious or buggy consumer could downcast).
**Fix:** `Object.freeze(Object.keys(EXTENSION_REGISTRY))` or
`Object.keys(EXTENSION_REGISTRY) as const` won't work for runtime arrays.
Use:
```ts
export const BUNDLED_EXTENSION_PROFILE_URLS: readonly string[] =
  Object.freeze(Object.keys(EXTENSION_REGISTRY));
```
Cosmetic — no current bug.

### IN-02: Misleading comment in `useConformanceRun.ts` — "Promise.all" claim re: latency

**File:** `src/hooks/useConformanceRun.ts:181-184`
**Issue:** Comment says "Pre-Step-3 placement keeps the value-set expansion
+ extension-load latency measurable as one async tick rather than
serializing them." But the code at lines 197-207 (extension loads) and
lines 217-232 (value-set expansion) are sequential `await`s — they ARE
serialized, not parallelized. The two `Promise.all` calls each parallelize
their OWN URLs but the two phases run back-to-back. The comment claim is
inverted.
**Fix:** Either parallelize the two phases:
```ts
const [extResults, vsResults] = await Promise.all([
  loadExtensionProfiles(extensionUrls),
  expandValueSets(profile, terminologyClient, vsCache),
]);
```
Or update the comment to reflect the actual sequential semantics:
```ts
// Pre-Step-3 placement: extension SDs need to be in hand before the
// per-resource validation in Step 5. The two await blocks (this one and
// VS expansion) are sequential — see ROADMAP for the parallelization
// follow-up if profile fetch latency dominates.
```

### IN-04: `as unknown as` cast pattern repeated 481 times in generated index.ts

**File:** `src/quality/profiles/extensions/index.ts:9-489`
**Issue:** Every entry repeats `as unknown as Promise<{ default: StructureDefinition }>`.
This is sanctioned (per PROJECT.md double-cast pattern and the script
comment at lines 167-174) because the trimmed JSONs lack required SD
fields. But repeating the type assertion 481 times in the generated
output: (a) bloats the file, (b) makes any future SD-type change require
re-running the codegen, (c) obscures the intent — readers see `unknown`
casts everywhere with no single place to verify why.
**Fix:** Hoist the cast once:
```ts
type LazyJsonImport = Promise<{ default: unknown }>;
type LazyProfile = () => Promise<{ default: StructureDefinition }>;

// Cast the entire REGISTRY object once at the boundary
export const REGISTRY: Record<string, LazyProfile> = {
  "https://...url1": () => import('./File1.json'),
  "https://...url2": () => import('./File2.json'),
  // ... 479 more, each a clean one-liner
} as unknown as Record<string, LazyProfile>;
```
Reduces line length by ~80 chars per entry, makes the cast intent
explicit, and centralizes the type-trust boundary. Update the codegen
in `fetch-mii-profiles.mjs:175-178` to match.

### IN-05: Potential test-flakiness — `extensionProfile.test.ts` test 5 relies on test execution order

**File:** `src/quality/profiles/__tests__/extensionProfile.test.ts:78-105`
**Issue:** Test 5 acknowledges the cache pollution from tests 2/3/4 and
uses `vi.resetModules()` to defend (lines 85-94 comment). But the `it()`
order in vitest is preserved by default, so this is fine TODAY. If anyone
ever sets `sequence.shuffle: true` in vitest config, or if vitest's
parallel-within-file changes default behavior in a future version, test 5
might run BEFORE the others and the comment's "tests 2/3/4 above warmed
the cache" assumption inverts.
**Fix:** Make test 5 self-contained by also calling `vi.resetModules()` in
a `beforeEach` for it specifically, or restructure as:
```ts
describe('dedup invariant', () => {
  beforeEach(() => {
    vi.resetModules();
    loaderSpy.mockClear();
  });
  it('calls loader exactly once for concurrent invocations', async () => {
    const fresh = await import('../index');
    const [a, b] = await Promise.all([
      fresh.getExtensionProfileForUrl(MOCK_EXT_URL),
      fresh.getExtensionProfileForUrl(MOCK_EXT_URL),
    ]);
    expect(a).toBe(b);
    expect(loaderSpy).toHaveBeenCalledTimes(1);
  });
});
```
This makes the invariant order-independent.
