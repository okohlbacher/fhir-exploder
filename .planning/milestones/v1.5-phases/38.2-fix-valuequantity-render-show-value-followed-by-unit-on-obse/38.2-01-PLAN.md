<objective>
Fix the value-rendering defect on Observation rows in the patient detail Laborbefund tab. Today, when a user opens an Observation with `valueQuantity: { value: 98, unit: 'mg/dL', system: 'http://unitsofmeasure.org', code: 'mg/dL' }`, the Human-readable view renders `mg/dL` (the UCUM code) without the measured value `98`. The `_sort=-date` regression closed in Phase 38.1 was masking this bug; once Laborbefund populates against live Blaze + Synthea, the defect is visible on every row with a UCUM-coded Quantity.

**Root cause (located during planner investigation):** In `src/components/explorer/ResourcePropertyTable.tsx`, the `RenderValue` function dispatches by structural shape. The "Coding (standalone, not in CodeableConcept)" branch at **line 121** (`if (obj.system && obj.code)`) matches before the "Quantity" branch at **line 176** (`if (obj.value !== undefined && obj.unit)`). FHIR R4 Quantity has both shapes simultaneously when the unit is UCUM-coded — i.e. virtually always for Synthea / live Blaze. The Coding branch fires first and renders only `obj.code` (= `mg/dL`) plus the system URL; the actual measurement value `obj.value` (= 98) is dropped on the floor.

**Fix scope:** Move the Quantity check above the Coding check (or strengthen the Coding guard to exclude Quantities). Make the Quantity branch handle all four input shapes per the success criteria. Add colocation regression tests. Re-walk Phase 33 Test 1 + Test 6 against the same live Blaze fingerprint as Phase 38.1.

Purpose: Close the rendering defect that masked behind Phase 38.1's `_sort=-date` fix. Restores the v1.5 milestone audit precondition that Laborbefund displays measurements correctly.

Output: Patched `RenderValue` Quantity dispatch + 4-case regression test fixture + Phase 33 HUMAN-UAT row append.
